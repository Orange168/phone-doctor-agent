## 一、愿景（一句话）

**把一部真实手机的感知与执行能力交给本地 AI 模型，让它成为"另一个有手机的自己"——7×24 在线、能决策、能进化、能处理真实业务。**

## 三、核心洞察

### 3.1 "数字分身"的本质

- **手机 = 手**：在真实世界里感知（屏幕/传感器）和执行（触摸/输入）
- **本地模型 = 脑**：理解屏幕、规划任务、做出决策
- **数据飞轮 = 记忆**：每次操作沉淀，越用越懂业务
- 合起来 = 一个真实设备 + 智能决策 + 持续进化的数字分身

### 3.2 与"固定脚本自动化"的本质区别

|| 固定脚本（uiautomator2/Appium） | 数字分身（mobile-agent + 本地模型） |
|---|---|---|
| 界面变化 | ❌ 脚本崩 | ✅ 看屏幕自适应 |
| 行为拟人 | ❌ 固定轨迹/间隔，易检测 | ✅ 动态决策，天然拟人 |
| 异常处理 | ❌ 卡死 | ✅ 识别并处理/通知人工 |
| 任务泛化 | ❌ 每任务写脚本 | ✅ 改 prompt 即可 |
| 进化能力 | ❌ 无 | ✅ 数据飞轮微调 |
| 成本 | 低 | 中（LLM 推理） |
| 速度 | 快 | 慢（推理延迟） |

## 四、技术选型

### 4.1 执行端：一加 10 Pro（= 国行 Ace Pro）

- **root**：KernelSU Next + Susfs（内核级隐藏，防检测）
- **屏幕流**：scrcpy（低延迟 30-50ms，root 后更强）
- **触摸注入**：第一阶段用 scrcpy 的 input；第二阶段内核级（改 input 子系统，拟人化）
- **UI 感知**：uiautomator dump（root 后全量 UI 树）+ 截屏双通道

### 4.2 决策端：3×4070 Super 48G GPU

- **视觉模型**：Qwen2.5-VL-7B（或 32B，单卡够）
- **决策模型**：Qwen 系列（动作规划）遇到难题交个更高级ai
- **推理框架**：vLLM / Ollama / llama.cpp
- **微调**：LoRA（7B/14B 轻松跑，48G 可并行）

### 4.3 Agent 框架

- 备选：Mobile-Agent / AppAgent / AutoDroid / 自研
- 关键：要支持**自定义屏幕流输入 + 本地模型接入 + 数据记录钩子**

### 4.4 数据飞轮

- 统一数据格式：`(screenshot.png, ui_tree.xml, action, result, error, timestamp)`
- 失败分类：界面变化 / 点错 / 风控拦截 / 超时
- 微调：LoRA on 决策模型，让模型学会"这类界面该怎么做"

## 六、关键风险与对策

| 风险 | 对策 |
|---|---|
| 屏幕流端到端延迟（1-3s） | UI 树优先 + 截图辅助，双通道感知 |

## 七、核心反检测模块：逆向检测面 → 针对性对抗（2026-08-25 更新）

### 7.1 核心认知（关键升级）

**从"笼统模拟环境指纹"升级为"逆向检测面，针对性对抗"。**

- 风控 App（抖音等）通过多种维度检测自动化，但**第三方 App 拿不到基站原始信息**（Android 10+ 限制），基站模拟不需要做
- 正确做法：**逆向目标 App APK，拿到它到底检测什么，只针对性模拟它真的检测的维度**，不做无用功
- 逆向是**持续工作**：App 更新会加检测，需定期重新核对检测面清单

### 7.2 检测面分析（抖音为主，持续更新）

逆向抖音 APK（jadx + Frida hook + AI 辅助分析）
  → 提取"检测面清单"（它到底查哪些）

按检测维度分类：
├─ root 痕迹（su/路径/进程/magisk） → Susfs 内核隐藏
├─ 系统属性（Build/secure/调试标志） → resetprop 改
├─ 文件/挂载 → Susfs 伪造
├─ 包名/进程 → 隐藏列表
├─ 传感器异常（长期不动/无变化）   → 内核伪造读数（真实数据回放）
├─ 屏幕/状态（方向/亮度/前台）    → 高权限模拟
└─ 行为特征（点击轨迹/频率/时序） → 拟人化执行（数字分身核心）

第三方 App 拿不到（不需要模拟）：
├─ 基站 Cell ID/信号强度（权限限制）
└─ 全局触摸事件（非 root/无障碍拿不到）

### 7.3 真实数据采集 → 模拟回放（拟人化数据源）

采集真人操作数据（root 后）：
├─ 触摸事件（坐标/压力/面积/时序）— root 全量
├─ 屏幕状态（方向/亮度/前台 App）
├─ 传感器（加速度/陀螺仪/光线）— 内核层
└─ 界面语义（UI 树 → "发布页/评论区/推荐流"）

标注：界面 → 语义，操作 → 意图

数据集：(界面语义, 操作序列, 时序特征, 结果)

投喂小模型：学会"真人在这种界面怎么操作" → 生成拟人行为

回放输出（高权限）：
├─ 内核伪造传感器读数（改驱动，一加内核源码支持）
├─ 屏幕状态模拟（高权限）
└─ 行为基线（个性化操作习惯）

### 7.4 关键原则

1. **精准 > 全面**：只模拟 App 真检测的维度，伪造它不查的反而引入不一致
2. **数据流 > 单值**：伪造要"符合真人分布的数据流"（时序+关联），不是静态值
3. **关联一致性**：多数据要协同（屏幕动 + 传感器动 + 行为动），不能孤立伪造
4. **主动拟真 > 被动伪造**：能让 agent 真的动（间歇亮屏/切换/操作）比伪造更好，物理数据天然自洽
5. **持续迭代**：App 更新 → 重新逆向 → 更新检测面清单 → 调整模拟

### 7.5 系统透明度与干预边界（源自 Verticalsky 案例复盘）

以下三条来自 Verticalsky 客户 APK so 冲突案例（session 3ba9515491f4），适用于数字分身所有系统级干预：

**1. app 知不知道，取决于"它有没有检测引擎"，不是"技术上能不能知道"**

- 打印 app（没检测引擎）→ 改文件、hook 它都不知情，不是藏得好，是**没人查**
- 抖音（每层都有引擎）→ hook 会被发现

**对数字分身**：别赌"藏得深"。先**逆向目标 app 到底查什么**（检测面清单），对着清单精准打。没写检测的不用防，写了检测的重点防——资源不浪费。

**2. 系统级干预的作用域铁律：只做目标进程，不要全局替换系统库**

案例中系统 libcrypto.so 一个字节没动，因为全局替换会波及 system_server/keystore/TLS，直接 Boot loop。

**对数字分身**：hook/注入/属性伪造永远只做目标 app 进程内（zygisk 按包名白名单、frida 按 target 注入、resetprop 仅在目标命名空间生效）。不要全局替换 `/system/lib` 里的库，不要全局 hook 系统 so。这是全局风险的底线。

**3. 竞品 A/B 对照法：遇到差异问题，两台设备对照，差异点就是根因**

案例最终根因不是"客户 so 坏了"，而是"一处 namespace 差异"（竞品 data app ISOLATED 命名空间 vs 系统 app SHARED 共享命名空间）。

**对数字分身**：遇到"为什么 A 平台能跑、B 平台不能"、"为什么抖音正常、快手检测到 root"，不要猜，**两台设备/两个场景做 A/B 对照，差异点就是根因**。对 root 隐藏、传感器伪造、namespace 隔离都适用。
